## localhost 是什么

`localhost` 表示正在访问网页的这台设备。现在电脑浏览器访问的是电脑本地运行的 Spring Boot。
手机输入同一 localhost 地址访问的是手机自己，不是电脑。网页形态不等于只能 localhost；
应用部署到可访问的服务器后，可用正式 HTTPS 域名访问，电脑和手机连接同一个后端。

## 建议顺序

1. 保留已获用户确认的本地网页 MVP 和 Spring Boot 后端，不因做 App 推倒重写后端。
2. 建立一套 Flutter 客户端（目录 client/），一开始包含 android/windows 两个目标；
   [client/ 离线演示骨架](../phase-1/client-scaffold.md) 已完成，用户反馈基本没问题；
   已接入 [真实账号与备忘录](../phase-1/client-api.md)，用户反馈其他交互基本没问题；
   现进一步实现 [前台自动同步](../phase-1/client-auto-sync.md)，76 项客户端检查及单独 10 项 HTTPS 合同验收通过，新版同步需用户确认。
   UI、模型和接口请求尽量共享；系统通知、定时、文件导入和窗口后台行为按平台适配，不能只生成空壳就称为双端完成。
3. 用户已同意 **USB + 本机 HTTPS**，现已用已有 JDK 准备开发证书，客户端保留证书校验；
   电脑后端只绑定 127.0.0.1:8443，安卓通过 ADB reverse 联调。没有系统证书安装、隧道启动或防火墙变更。
   自动验收使用临时 H2，不碰学习数据库；手动 App 验收建议新建专用账号。这里只共享本机数据，不公开弱密码账号。
   cloudflared 仍是可选网页路线，Quick Tunnel 邮箱验证不直接用于原生 API 请求，不为 App 绕过限制开放匿名公网入口。
   已确认 vivo X100s/OriginOS 5 为 Android 15/API 35，用户确认独立测试 APK 安装与交互通过。
   正式两端复用现有认证、备忘录与统一保存接口；保留会话、CSRF 和用户隔离，
   不为了手机客户端自动换成 JWT、关闭 CSRF 或开放任意来源 CORS。
4. 分别补两端主动提醒：安卓系统通知与设备端定时，Windows 主窗口关闭后留托盘的后台提醒。
   手机验证后台、锁屏、省电与权限；电脑验证关窗口、彻底退出、系统通知、声音与启动恢复。
   不把关闭窗口等同退出进程，不承诺休眠/关机或强行停止后一定准时。
   验证已同步到手机的任务在退到后台、锁屏时的行为。
   本地定时不等于服务端推送：电脑端改期、取消后，离线手机可能仍持有旧计划，需要设计版本校验、
   同步和去重。通知权限、精确闹钟权限、系统省电、强行停止及重启分别验证，不承诺所有状态绝对准点。
   平台依据见 [Android 定时任务](https://developer.android.com/develop/background-work/services/alarms) 和
   [通知权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)。
5. 需要电脑关机后仍在线同步、调度与推送时，再部署常驻后端与数据库，配置 HTTPS、稳定地址、
   进程启动/重启、日志和备份；评估适合目标设备与网络的推送渠道，分开记录渠道接受、设备展示和已读。
   可以先运行 Java 21 + 应用 JAR，不要求先把应用 Docker 化；服务器、域名和费用另行确认。
6. 在安卓闭环验证后推进 iPhone。PWA 可以作为可选网页入口，但不是当前最终交付目标，
   不把“添加到桌面”称为已完成安卓 APK 或 iPhone App。

## 临时 HTTPS 入口的边界

Quick Tunnel 无需自己的域名或 Cloudflare 账号，临时主机名每次创建会变化，停止进程后地址失效；
没有运行可用性保证。测试期间电脑、MySQL、后端和隧道进程仍需运行，访问流量会经过 Cloudflare。
邮箱访问限制需要交互式浏览器验证，不适用于直接发请求的非交互客户端；因此先用于浏览器联调，
原生 App 的 API 联调方式另行选择，不能照搬成免认证的公开接口。
依据见 [Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)。

vivo 自带浏览器或夸克可以先尝试打开网页，但版本、编解码、文件导入与通知能力需真机验证。
不能推断它们支持 Web Push，也不要求用户下载 Chrome；网页前台声音与 App 后台提醒是不同验收项。
局域网测试也不关闭防火墙、不开放数据库 3306 到公网，不安排通过普通明文 HTTP 传输账号密码。

服务器不是多端同步的全部：当前数据库共享读写已存在，但编辑冲突检测、离线同步、标签页统一响铃仍待实现。
系统通知与缓存/MQ 是不同问题；没有测量依据，不为了部署或 App 提前引入 Redis、Kafka 或搜索服务。

## 上线前要补的事

- 本地学习的 1 字符密码下限必须重新评估；补齐登录保护、账号恢复与安全配置验收。
- 使用 HTTPS，检查会话 Cookie 的 Secure 等配置，保留同源与 CSRF，不靠开放 CORS 解决部署。
- 密码、密钥通过运行环境管理，不提交 Git、不写进日志；生产关闭不必要的调试日志。
- 数据库仅在必要的私网/主机网络可达，持久化并验证备份恢复，不公开暴露 3306。
- 手机真机、服务重启、通知权限拒绝和设备离线分别验收，明确无法保证的提醒场景。
- 现有 MySQL 学习数据不会自动迁移到服务器；若需迁移，单独确认范围并先备份。
- 偏好和导入文件目前仅在浏览器来源下保存；从 localhost 换域名后需重新导入，尚无云端素材同步。

手机联调、App 工具下载与正式部署分开确认；同意下载 cloudflared 不等于同意开放公网、购买服务或下载 Android SDK。
