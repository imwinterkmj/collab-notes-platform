# 业务范围与提醒设计

## 项目定位

做一个支持电脑和手机使用的备忘录与定时提醒平台，通过实际业务学习后端工程、多端数据
一致性、可靠任务处理和高并发保护。

典型场景：在电脑上创建“周五下午面试”，设置提前半小时提醒；手机查看和修改同一条
备忘录；到时间收到通知，在任一端标记完成后，其他设备能获取新的状态。

本文件描述整体产品范围和演进原则。当前阶段 0 已完成，阶段 1 已完成注册、登录以及
完整备忘录管理、一次性提醒、站内通知与同源网页并自动验证用户隔离；本地网页统一验收已获用户确认。
不同设备可分别建立会话，不表示实时刷新、离线同步或并发冲突处理已实现。
已实现状态以 `PROGRESS.md` 为准。
当前启动与网页验收见 [阶段 1 MVP](../phase-1/mvp.md)，站内通知不等于系统推送。
当前也已实现 [常驻卡片、声音与电脑桌面提醒](../phase-1/active-reminders.md)，需用户主动开启，
用户反馈基础体验基本没问题，不能推断覆盖所有设备。保持网页打开才能尝试提醒；关页/休眠/锁屏实时推送尚未实现。
新增 [齿轮设置、大弹层与个人铃声/图片导入](../phase-1/reminder-settings.md)，内置选项保留，
偏好/素材副本只在当前浏览器按账号读取，不上传、不跨设备同步；本机体验已获用户确认，手机尚未实测。
当前主页按未完成/更新时间排序，点击记录打开编辑弹窗；[回收站](../phase-1/editor-and-trash.md) 保留每账号最近 30 条删除快照，
恢复内容与完成状态但不恢复旧提醒/通知；超过容量的最早记录永久移出，不是按 30 天到期。

## 基础领域职责

| 概念 | 职责 | 引入时机 |
| --- | --- | --- |
| 用户 | 身份认证、数据归属与访问隔离。 | 阶段 1。 |
| 备忘录 | 标题、正文、完成状态及创建修改信息。 | 阶段 1。 |
| 提醒任务 | 提醒时间、关联备忘录及任务处理状态。 | 阶段 1，先支持一次性提醒。 |
| 站内通知 | 持久化提醒结果，用户进入应用后可以查看。 | 阶段 1。 |
| 标签 | 分类与筛选。 | 基础闭环完成后加入。 |
| 设备订阅 | 管理具体设备的推送订阅与失效信息。 | 接入真实系统推送时。 |
| 投递记录 | 记录某次提醒到某渠道、设备的尝试结果及重试。 | 可靠投递演进时。 |

这里先约定职责，具体表名、字段、状态枚举和 API 在对应阶段设计。备忘录的完成状态、
提醒任务的执行状态、通知的已读状态是不同概念。

## 第一版功能边界

- 注册、登录；访问每条备忘录和提醒都校验所属用户。
- 创建、修改、删除、查询和分页展示备忘录，支持完成与未完成状态。
- 为备忘录设置一次性提醒，支持修改时间、取消、完成后停止未触发的提醒。
- 提醒任务保存在 MySQL，后台周期性查询到期记录，触发后生成可查询的站内通知。
- 备忘录变化与关联提醒变化需要有明确事务边界，不能只更新其中一方。
- 服务恢复后可以查询未处理任务，并按约定的过期策略处理。

第一版先使用单体、单个调度实例建立正确性基线。站内通知只证明后端触发结果已经保存，
不代表关闭网页后的手机锁屏通知。站内通知闭环完成后，再分步接入跨端界面和真实推送。

暂不把多人工作区、知识库协作权限、分享链接作为核心业务。重复提醒、稍后提醒、离线
编辑、复杂时间规则等属于后续增量范围。

当前没有云服务器或域名，cloudflared 和安卓开发工具已分别获准下载，普通 SDK 许可已获准接受；
没有开放入口或部署，生成的环境验收示例 APK 不是正式备忘录 App。

基础版本先保证在线读取和修改正确；已用长轮询解决 App 前台手动刷新问题，容量仍待测量。页面关闭
后的提醒需要设备级能力。已同步任务可由 App 安排设备端提醒；跨设备改期、取消与新任务仍需同步或推送。
设备离线时的旧计划、通知权限与省电限制必须单独处理，不把本地定时与服务端推送混为一谈。
电脑关页提醒保留目标，拟由 Windows 客户端托盘后台实现；关闭主窗口不等于彻底退出，关机/休眠不承诺准时响铃。

服务端统一保存可明确比较的时间点；用户输入的时区需要明确转换。第一版先约定时间精度
和显示方式，再扩展时区、夏令时和重复提醒规则，不把本机时区当作所有用户的时区。

## 提醒语义与竞态

业务设计和测试需要明确以下边界：

- 提醒改期：旧时间对应的任务不能不经校验就继续发送。
- 取消、完成、删除：停止尚未执行的任务；已经提交给外部渠道的通知可能无法撤回。
- 并发修改：电脑和手机都基于旧版本修改时，后续通过版本号检测覆盖风险。
- 重复请求：重复点击或网络重试不能无意创建多份相同任务。
- 过期处理：服务停机或渠道故障后，哪些提醒补发、哪些过期，以及如何告知用户需明确定义。
- 重复调度：多个实例抢任务、进程崩溃和超时重试，需要任务认领与恢复机制。
- 多设备投递：同一次提醒向电脑和手机各发送一次可能是预期行为；对同一目标的重复尝试
  才需要按投递语义去重。唯一标识应覆盖提醒实例、渠道和目标设备。

具体实现按阶段推进。特别是外部渠道返回超时后，不能直接断言未发送；内部去重也不能
独自保证外部通知绝对只展示一次。测试和产品行为需要承认这些边界。

## 推送链路的成功定义

| 观察点 | 含义 |
| --- | --- |
| 提醒到期 | 已达到计划时间。 |
| 开始调度 | 后台开始处理对应任务。 |
| 站内通知入库 | 应用内通知已持久化，可供客户端读取。 |
| 渠道接受 | 推送服务接受了请求，不等于设备已收到。 |
| 设备收到 | 只有存在相应回执时才能记录。 |
| 用户已读 | 需要用户或客户端的明确操作，不能从发送结果推断。 |

服务端调度延迟与设备到达延迟分别记录。设备离线、权限关闭、系统省电或渠道故障都可能
影响提醒展示；指标不使用无法获得的设备回执作为已验证结果。

## 面试问题与实验场景

| 场景 | 研究问题 | 对应实验 |
| --- | --- | --- |
| 双端修改备忘录 | 更新丢失、乐观锁、事务。 | 同版本并发更新并检查冲突结果。 |
| 请求重复提交 | 请求幂等、唯一约束。 | 重复请求及超时重试。 |
| 改期与发送同时发生 | 状态机、版本校验、取消边界。 | 控制执行顺序构造竞态。 |
| 多任务集中到期 | 批处理、调度吞吐、背压。 | 同一时间窗口内生成大量到期任务。 |
| 多个调度实例 | 任务认领、租约与崩溃恢复。 | 同时抢占并在认领后中断进程。 |
| 保存成功但发布失败 | 事务发件箱、补偿。 | 在数据库提交与发布间注入失败。 |
| 重复消费与渠道超时 | 消费幂等、重试、故障隔离。 | 重投消息、模拟超时与限流。 |
| 大量历史数据 | 联合索引、分页、归档、分片。 | 10 万、100 万记录下对比执行计划与耗时。 |

## 性能测量口径

- 大数据量：记录总行数、数据分布和查询条件，研究数据库访问成本。
- 请求并发：记录并发数、请求速率、QPS、P50/P95/P99 和错误率。
- 提醒突发：记录到期分布、每秒任务处理数、调度延迟分位数、积压量和恢复耗时。
- 投递可靠性：记录发送尝试、渠道接受率、重试、过期、重复处理与失败原因。

例如“模拟一分钟内 10 万条提醒到期”只是一种实验负载，平均约为每秒 1,667 个提醒任务，
不等于 API QPS，也不代表系统已经能够承载。多设备投递和重试会增加实际发送尝试数量。

在记录运行环境、索引、数据分布、并发与持续时间后，才比较优化结果。对未接入的外部
服务使用明确标注的模拟渠道，不把模拟吞吐量等同于真实设备通知能力。
